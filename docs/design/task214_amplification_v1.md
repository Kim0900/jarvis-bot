**회로차단(프로세스 전역, 호스트 단위)**

## 4. 원인 특정 측정 (설계 중 가장 가치 있는 부분, 읽기 전용, 무비용)
1. `pg_stat_io`(PG17): 백엔드 유형별(client backend / checkpointer / background writer / walwriter / autovacuum worker) 읽기·쓰기·fsync 횟수와 시간(`track_io_timing` 필요 시 확인). 앱이 아닌 어느 유형이 쓰는지 직접 보인다. 2회 스냅샷(1시간 이상 간격)의 차이로 시간당 값을 구한다.
2. `pg_stat_bgwriter`/`pg_stat_checkpointer`: 체크포인트 횟수·쓰인 버퍼·sync 시간.
3. `pg_stat_user_tables`를 **전 스키마**로(auth·storage·realtime 포함) — 지금까지는 public 위주.
4. `pg_stat_activity`의 `application_name`·`usename`별 활성 연결 수와 쿼리 주기(앱/Supabase 내부/에이전트 분리).
5. 대표 대시보드: 10/12~13 급등 시각의 **시간 단위 Disk IO 그래프**(보류 중인 요청).
6. Supabase 지원 문의(무료): "매일 16:30~19:30 호스트 I/O 정지(체크포인트 20초, autovacuum 지연), 프로젝트 ref, 3일치 로그 근거" — 무료 플랜 문의 가능 여부는 미확인. 근거 자료는 마기 #5478·#5662에 있음.
7. 앱 요청 카운터: 호출부별(라벨)·시간별 집계를 로그/`scheduler_status` 비침투 방식(로컬 메모리+정시 1줄 로그)으로 — 7·8번 미집계 해소.
**판단 게이트(사전 등록)**: ① `pg_stat_io`에서 client backend 쓰기·읽기가 전체의 낮은 비율이고 checkpointer·walwriter·autovacuum이 대부분이면 앱 감축은 IO를 못 줄임 → B 재권고 근거 강화 또는 지원 문의 결과 대기. ② client backend가 지배적이면 R1/R2를 우선 적용하고 재측정.
