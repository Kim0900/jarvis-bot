## 0. 먼저 정직하게: 이 작업이 할 수 있는 것과 없는 것
- **(가설, 관측 아님)** 앱 코드의 주기 호출을 코드에서 더하면 **하루 약 6천 요청(분당 약 4)** 이라는 *산술 추정치*가 나오고, DB 전체 트랜잭션은 분당 약 45이므로 앱이 약 10%일 것이라는 *추정*이 따라온다. 이 수치는 분자가 코드 산술이고 분모가 DB 전체 통계라서, **누가 보낸 호출인지 구분하는 계측이 없는 한 앱 몫이라고 귀속할 수 없다**(PostgREST 경유 요청은 DB에서 모두 같은 연결 풀로 보인다). DB 전체 누적치(blks_read 1,580, WAL 일 평균 약 1 MB 등)도 앱에 귀속되지 않는다. 따라서 감축안이 Disk IO 73%를 내릴지에 대한 예측은 **하지 않는다**(내린다는 근거도, 내리지 못한다는 근거도 아직 없다 — 마기 #5467·#5474의 신중한 결론과 같다).
- 장애 로그의 모양(체크포인트 2버퍼 쓰기에 20초, `BEGIN` 최대 19~25초, autovacuum 기동 지연, 시작은 가변(10/19는 14:15, 마기 #5687)이고 종료는 19:26/19:28/19:29/19:28로 거의 고정)은 **호스트 수준 I/O 정지와 일치하는 형태이나, 현재는 가설이다**(상관 측정과 지원 확인 전까지 확정하지 않는다). 앱 호출이 원인이라는 증거는 못 찾았고, 정지 중에 호출이 쌓여 풀(PGRST003)을 고갈시키는 **증폭** 가능성이 로그에 보인다.
- **추론 정정(카산드라 #5706)**: `pg_stat_io`에서 client backend의 직접 쓰기가 0이라는 사실은 **앱의 쓰기·갱신이 shared buffer를 더럽혔고 그 쓰기를 나중에 checkpointer가 내보냈을 가능성을 배제하지 못한다**. checkpointer 쓰기는 출처(앱/PG 내부)를 귀속시킬 수 없다. `pg_stat_io`는 누적 relation I/O이지 호스트 디스크 성능이 아니며, 단일 스냅샷으로 16:30~19:30 정지의 원인을 정할 수 없다. 따라서 앞선 "checkpointer 지배 → 앱 감축 무효" 판단 게이트는 **철회**하고 4절의 상관 측정으로 대체한다.
- 따라서 아래 안은 ① 정지 중 증폭 억제(재시도 정책·회로차단) ② 쓸모없는 상시 호출 제거(atlas 폴링) ③ **원인 특정 측정(`pg_stat_io`)** 순으로 구성한다. "원인 해소"가 아니다.

- **열림 중 사용자 요청 규약(v1.2, G214-02)** — 무제한 통과가 아니라 아래 예산 안에서만 DB에 간다:
  1. **동시성 상한 2**(호스트 단위 세마포어). 초과분은 **기다리지 않고** DB 호출 0으로 즉시 "DB 불안정, 잠시 후 다시" 응답(v1.4: 입장 판정은 비블로킹).
  2. **예외 예산(v1.3 정정, G214-04)**: 호스트 전체 토큰 버킷, 용량 B=3, 토큰 1개당 c=10초 보충, 정수 나노초 연산(부동소수 없음), 락 안에서 판정. **보장 수식은 "분당 6건"이 아니다.** 가득 찬 버킷에서는 임의의 닫힌 구간 T초 안에 **N(T) ≤ B + ⌊T/c⌋ = 3 + ⌊T/10⌋** 건까지 통과한다(최악, 도달 가능: 1초 3건, 10초 4건, 59.999초 8건, **60초 9건**, 600초 63건, 3600초 363건). 이미 비워진 정상상태에서는 60초 7건이고 장기 평균은 분당 6건(시간당 360). 소진되면 DB 호출 0으로 즉시 거절. 반열림 프로브는 이 예산에 포함하지 않으며(별도 한도: 최소 60초 간격) 구간 L초의 프로브는 ≤ ⌊L/60⌋+1. **따라서 열림 구간 L초의 DB 호출 상한 = (3 + ⌊L/10⌋) + (⌊L/60⌋ + 1)**. 시뮬레이션(1 ms 해상도 1시간 + 무작위 도착 300열 + 8스레드 경쟁)이 경계 1초·10초·59.999초·60초에서 이 수식을 재현했고, v1.2 문장("분당 6건, 상한 6×분+프로브")은 60초에 9건이 나오므로 **거짓**임을 확인했다(9절).
  3. **절대 마감과 강제 종료(v1.4 정정, G214-05·07)**: 단일 시도, 재시도 없음. 단계별 타임아웃(연결 3초·읽기 5초)은 **합이 총합을 막지 못하고**, 바이트가 오는 한 읽기 타임아웃은 매번 재설정되므로 느린 드립에서는 총시간이 무상한이다(실측: 핸드셰이크 2.8초+응답 4.8초=7.65초 성공, 1바이트/초 본문 20초). 그래서:
     - **절대 마감 5.0초**(단조 시계): 예산·동시성 입장이 **비블로킹으로 통과한 순간**부터 흐르며 풀 대기·TLS·헤더·본문 끝까지 포함한다. 단계별 타임아웃은 보조(실측: 핸드셰이크 드립은 연결 타임아웃 3초가 먼저 끊는다).
     - **호출자 복귀와 정리의 분리(v1.5, G214-09)**: 각 DB 호출은 별도 태스크로 돌고, 마감은 **타이머**(`call_later`)가 집행한다. 타이머가 울리면 **그 순간** 호출자의 결과를 \"deadline\"으로 확정해 돌려보낸다 — 호출자 복귀 시각 = 마감 + 스케줄링 지터뿐이며(허용 80 ms, 실측 5.006초·최악 2.8 ms 초과) **취소 완료를 기다리지 않는다**. 같은 순간 백그라운드에서 `cancel()`을 보내고, 그 뒤 GRACE(0.2초)에 **다른 타이머**가 태스크가 아직 살아 있으면 정체(stuck)로 센다. 호출자 지연 계약(5.0초+지터)과 정리 계약(취소 → 연결 닫힘 → 허가 회수, 정리가 오래 걸리면 정체로 계상)은 별개다.
     - **마감 경계 규칙**: 결과는 호출당 **정확히 한 번** 확정된다(먼저 오는 쪽이 이김: 태스크 완료 또는 마감 타이머). 마감 뒤에 도착한 정상 결과는 **버리고** `late_discarded`로 센다(읽기 전용이라 해가 없음). 마감 뒤에 나는 예외도 회수해 \"never retrieved\" 경고를 남기지 않는다. 시험: 마감 50 ms 전 종료 → ok, 50 ms 후 종료 → 마감에 deadline 반환+결과 폐기(D10), 마감 ±10 ms에 몰린 300건에서 이중 확정 0·미회수 예외 0(D11).
     - **같은 규약이 모든 DB 호출 종류에 적용**된다: 사용자 예외 호출(마감 5.0초), 반열림 프로브(마감 5.0초, 프로브 전용 허가 1개이며 사용자 상한 2에 넣지 않음), 배경 폴링·순라(현행 일률 타임아웃 15초와 같은 15.0초 절대 마감 — **제안**, 구현 전 마기 확인). 호출 종류별 마감 값만 다르고 복귀/정리 분리·허가 회수·정체 계수·경계 규칙은 같다.
     - **허가는 태스크가 실제로 끝날 때 반환**(done-callback): 마감 시각이 아니다. 따라서 동시 DB 요청 상한 2는 취소를 무시하는 태스크가 있어도 거짓이 되지 않는다. 상한만큼(2개) 정체되면 새 요청은 기다림 없이 거절(DB 호출 0, fail-closed)되고, 태스크가 실제로 끝나면 자동 복구된다(시험 D7: 정체 2개 중 세 번째 호출 0.0 ms 거절, 종료 후 정상 입장). 정리가 3초 걸리는 취소도 호출자는 5.0초에 돌아가고 허가는 정리가 끝난 8초경에 회수되며 그동안 정체로 계상된다(D12). 400건이 동시에 취소를 무시해도 호출자 지연은 늘지 않는다(D13, 시간 축소 시험).
     - **스레드 경로 금지**: 앱의 Supabase 호출은 비동기 클라이언트만 쓴다(정적 검사 D9: `sb_*` 12개에 `to_thread`·동기 httpx·requests 없음). 스레드로 도는 호출(OCR·LLM)은 DB 호출이 아니며 이 규약의 대상이 아니다. DB 호출을 스레드로 옮기는 변경은 이 문서의 상한 보장을 깨므로 구현 시험(D9)이 막는다.
     - **단계적 격상(회복 절차)**: ① 마감+취소(정상) → ② 정체가 생기면 로그·계수기(`db_stuck_total`)에 기록 → ③ 공유 클라이언트를 `aclose()`해 진행 중 연결을 강제로 끊는다(실측: 드립 요청이 즉시 ReadError로 종료, D8)하고 새 클라이언트로 교체 → ④ 정체가 60초 넘게 풀리지 않으면 `/health`를 저하로 표시하고 기존 "DB 연결 불가" CRITICAL 1건에 정체 수를 붙임(새 알림 없음) → ⑤ 최후는 플랫폼 헬스체크에 의한 프로세스 재시작. ③~⑤는 설계이며, 이 문서 시점의 시험은 ①~③(D2~D8)까지다.
     - 마감 초과/취소는 "결과 불명"이므로 읽기에만 쓰이고(쓰기는 이 경로에 없음), 회로 실패 1회로 센다(중복 계상 금지).
  4. **범위**: 열림 중에는 **멱등 읽기만** 통과. 멱등이 아닌 쓰기·엄격 쓰기·CAS는 보류(거절+안내, 시도하지 않음).
  5. **억제**: 같은 사용자·같은 명령의 10초 내 중복은 하나로 합친다(첫 응답을 재사용 또는 거절). 거절·합침은 DB 호출 0.
  6. **저하 경보**: 열림 중 예산 소진·거절 수를 회로 상태 로그와 계수기에 기록하고, 기존의 "DB 연결 불가" CRITICAL 1건에 거절 누적 수를 갱신해 붙인다(새 알림을 만들지 않음, 30분 쿨다운 유지). 회복 알림에 열림 시간·거절 건수·예산 소진 횟수를 넣는다.
  7. 닫힘으로 돌아오면 예산·세마포어를 초기화한다. 예산 코드의 오류가 요청을 막지 않도록, 예산 계수기 자체 예외는 "거절"로 처리(fail-closed)한다.
- 순라 연동: 열림 중에는 개별 `patrol_internal_*` 자체 실패 경보를 만들지 않고 "DB 연결 불가(회로 열림, 시작 시각·누적 시간)" **1건**만 프로세스 로컬 쿨다운 30분으로 텔레그램 통지(PR#75의 장부 불가 통지와 같은 경로). 회복 시 "복구, 지속 시간 N분" 1건.
- **원자성·동시성(v1.1, 카산드라 A3)**: 회로 상태(`closed/open/half_open`, 연속 실패 수, 열림 시각, k)는 **호스트별 객체 1개**(프로세스 전역 사전, 키=호스트)이며 모든 전이는 하나의 `threading.Lock` 안에서 일어난다(이벤트 루프 스레드와 `to_thread` 스레드가 같이 쓴다). 반열림 프로브는 **락 안에서 `probing=True`를 먼저 세운 한 요청만** 수행한다(다른 요청은 열림 취급, 즉시 `CircuitOpen`). 프로브 실패 시 k+1, 성공 2회 연속 시 닫힘. 닫힘 구간의 실패 카운트 창은 단조 시계(`time.monotonic`)로 계산한다. 5xx 집계는 요청 단위로 정확히 1회만 센다(재시도 래퍼와 중복 계상 금지).
- **재시도 금지 범위(v1.1)**: 결과가 불명한 쓰기(타임아웃·연결 끊김 후의 POST/PATCH)와 PR#75의 CAS·`sb_write_strict`는 어떤 경우에도 재시도하지 않는다. 회로는 "새 시도를 막는 것"까지만 하고 진행 중이던 요청의 결과는 건드리지 않는다. **`_patrol_read_events`의 기존 일관성 재시도 동작은 독립 시험 없이는 바꾸지 않는다**(R3는 그 함수의 재시도 로직을 덮어쓰지 않고, 회로 검사는 그 바깥 호출 단위에서만 한다).
- **경보 유지**: 회로가 열려도 "DB 연결 불가" CRITICAL 1건(열림 시각·누적 시간 포함)과 회복 알림은 **반드시 유지**한다. 순라 자체 경보 전체를 침묵시키지 않는다. 15분 관측 지연(마기 자동검토 15분 stale)을 감시 한도로 기록한다.
- **필수 시험(구현 단계 제출 조건)**: 502/503/504/PGRST002/PGRST003/57014 각각 열림 조건 · 200 중간 끼어듦 시 초기화 · 정확히 5번째에 열림 · 동시 5xx 폭주에서 중복 전이/중복 알림 없음 · 반열림에서 동시 N요청 중 프로브 1건만 통과 · 프로브 실패/성공 2회 · 쓰기 미재시도(POST 타임아웃 후 서버 수신 횟수 1) · CAS UNKNOWN 보존 · 관측 지연(15분) 동안의 경보 지속 · `sb_get_all_strict` 완전성 검사 유지(회로 열림이 "빈 결과"로 둔갑하지 않고 예외) · 지연/침묵(응답 없음)에서 타임아웃 후 전이 · (v1.2) 열림 중 예산 소진 시 DB 호출 0 · 동시 N요청 중 상한 2만 통과 · 비멱등 쓰기 보류 · 10초 내 중복 억제 · 토큰 보충 · 열림 1시간 시뮬레이션에서 DB 호출 수 ≤ U(3600)+P(3600)=424(구간 수식, 60초 창 ≤ 9) · 1초/10초/59.999초/60초 경계 시험 · 무작위 도착에서 수식 비초과 · 느린 핸드셰이크+느린 응답의 종단 5.0초 · 느린 본문(드립) 5.0초 · 세마포어 대기 포함 마감 · (v1.4) 느린 본문·느린 헤더·핸드셰이크 드립·무응답에서 절대 마감 5.0초와 허가 반환 · 50건 동시 호출에서 서버 도달 ≤ 2 · 취소 무시 태스크의 정체 계수·fail-closed·복구 · 클라이언트 `aclose()` 강제 종료 · DB 호출 스레드 금지 정적 검사 · 문서 수식 일관성 검사 · (v1.5) 호출자 복귀는 마감+지터(≤80 ms)이며 취소·정리를 기다리지 않음 · 마감 50 ms 전/후 종료 · 마감 ±10 ms 몰림 300건에서 이중 확정 0·미회수 예외 0 · 정리 3초 · 400건 동시 취소 무시 · 정체는 타이머로 판정 · 닫힘 후 초기화 · 예산 계수기 예외 시 fail-closed.
- 공유 `httpx.AsyncClient`(keep-alive, `max_connections` 4, 단계별 타임아웃은 보조이며 사용자 요청 경로의 총시간은 위 2절 3항의 5.0초 종단 마감이 정한다)로 새 연결 폭주를 막고, 오류 로그는 상태코드·테이블·지속 횟수만(본문 200자 제한, 같은 오류 분당 1줄로 집계).
- **한계(공시)**: 회로차단은 DB를 낫게 하지 않는다. 정지 구간 동안 우리 쪽 대기 스레드·풀 점유를 줄일 뿐이며, 순라 감시 해상도가 정지 중 낮아진다(최대 600초 간격 프로브). 감시 지연 한도: 장애 감지는 최대 5분+프로브 간격(≤ 600초). 회로가 닫히는 순간 즉시 1회 **따라잡기 폴링**을 한다(아래 R1, 9절 C4).

- **사전 등록 목표(측정 가능, v1.2)**:
  - **기준선(필수 선행)**: R0 적용 후 최소 7일 연속의 호출처별 일별 계수(`poll`/`wake`/`user`/`patrol`/`job`)와 같은 기간 `pg_stat_statements` 델타(참고용 — 클라이언트 귀속 불가, 통계 reset 시 폐기). 기준선이 없으면 아래 감축 목표를 평가하지 않는다. 현재의 2,880·약 6,100은 코드 산술 **추정치**이며 목표의 기준값으로 쓰지 않는다.
  - **① atlas 정기 폴링(`caller=atlas, kind=poll`) ≤ 300회/일**(300초 주기 = 288 + 백오프는 줄이기만 함). 폴링 계수는 깨움과 **분리해서** 센다.
  - **② atlas 즉시 깨움(`kind=wake`)**: 정상 동작에서 늘 수 있으므로 일일 상한을 두지 않고 **기대 구간**으로 관리한다. 기대 구간 = 기준선 7일 동안의 일별 `save_atlas_report` 건수 최소~최대. 깨움 읽기가 기대 구간 최대의 3배를 넘으면 경보(원인 조사 대상). 단 폭주를 막는 **하드 한도**로 깨움 읽기는 토큰 버킷(버스트 3, 60초당 1회 보충 → 임의의 T초 구간 **N(T) ≤ 3 + ⌊T/60⌋**, 1시간 63건, 하루 평균 1,440회 + 버스트 3)을 둔다. 버킷이 비면 그 깨움은 버려지지 않고 **다음 정기 폴링에 합쳐진다**(보고서 처리는 최대 5분 지연, 유실 없음).
  - **③ atlas 합계 = 폴링 + 깨움**: 목표는 "폴링 ≤ 300 **그리고** 합계 ≤ 300 + 기대 구간 최대 × 3"으로 둔다(깨움이 정상일 때 상한이 깨지는 문제를 피함). 정상 즉시 깨움이 있어도 ①은 성립해야 한다.
  - **④ 앱 합계**: 위 호출처별 계수의 합으로 정의한다(DB 전체 통계가 아님). 감소 목표 수치는 기준선 확보 후 마기가 정한다(사전에 3,300을 못 박지 않는다 — 분모인 6,100이 추정이므로).
  - **⑤ 정지 재현 시** 회로 열림 구간 L초의 DB 호출 수 ≤ U(L) + P(L), U(L)=3+⌊L/10⌋(사용자 예외 예산), P(L)=⌊L/60⌋+1(프로브) — 2절 2항이 **유일한 정의**이며 이 목표·경보 임계·구현 승인 시험은 모두 이 식을 참조한다(L=60→9+2, 600→63+11, 3600→363+61). 깨움 예산은 같은 형태 W(T)=3+⌊T/60⌋.
  - **Disk IO %는 목표로 두지 않는다**(0절). R1 전후 비교는 **같은 부하 조건의 시간창끼리**(같은 요일·시간대, 정지 유무를 따로) 하고 불확실성(일별 변동·캐시 상태)을 함께 적는다. 대시보드 IO 그래프가 변하지 않았다는 사실은 "원인이 앱 밖"을 **증명하지 못한다**(기준선·캐시 효과 때문). 결론 문구는 "R1은 IO 하락 효과를 보이지 못했다(관측 구간·오차 명시)"까지만 쓴다.
- 쓰기 감소 안은 제안하지 않는다: 앱 쓰기는 분당 0.4건이라 감소해도 의미 없고, 하트비트는 순라·/health의 사각 감시 신호다.

## 4. 원인 특정 측정 (v1.1: 상관 측정으로 재설계, 읽기 전용, 무비용)
**원칙**: 모든 값은 **같은 `stats_reset`(현재 2026-02-12 23:51:26Z) 기준 누적치의 시각 찍힌 스냅샷 델타**로 다룬다. 초당 값 = (후 − 전) / 경과초. stats_reset이 바뀌면 그 쌍은 폐기한다. 단일 스냅샷으로는 아무 원인도 정하지 않는다.
**스냅샷 세트(한 번에 한 트랜잭션 안에서, 읽기 전용)**: `pg_stat_io` 전 행(backend_type·object·context별 reads/writes/extends/fsyncs/*_time), `pg_stat_checkpointer`(num_timed, num_requested, write_time, sync_time, buffers_written), `pg_stat_wal`(wal_records, wal_bytes, wal_fpi, wal_buffers_full; PG17에서 WAL write/sync 시간은 pg_stat_io의 wal 객체), `pg_stat_bgwriter`, `pg_stat_database`(xact_commit/rollback, blks_read/hit, tup_*, temp_*), `pg_stat_activity` 집계(`application_name`·`usename`·state별 수), `pg_stat_statements` 상위(총시간·호출수·rows 기준 20), 전 스키마 `pg_stat_user_tables`(auth·storage·realtime 포함), `now()`, `pg_postmaster_start_time()`, `pg_is_in_recovery()`.
**시각 계획**: 정상 구간 전(예: 15:30) · 정지 중(최소 2회: 17:30, 18:30) · 정지 직후(19:35) · 정상 후(21:00)에 각 1세트(연결이 막히면 실패 사실과 시각도 기록). 이로써 구간별 초당 델타를 비교한다. 정지 중 연결 불가는 그 자체로 측정치(타임아웃 시각 기록).
**호출처 귀속에 관한 주의(v1.2)**: 이 스냅샷 세트는 DB 전체 통계라 클라이언트별로 쪼갤 수 없다. 앱 몫·외부 몫의 비율은 R0 계수기가 생기기 전에는 주장하지 않는다.
**외부 자료(필수)**: 대표 대시보드의 **Disk IO 예산/소진 그래프와 시각 단위 값**(캡처, 정지 전·중·후), Supabase 지원 문의 답변(무료 가능 여부 미확인 — 문의 가능하면 프로젝트 ref와 3일치 로그 근거로 "매일 19:26~19:29 종료"의 플랫폼 측 원인을 질의).
**앱 쪽 분모**: 앱 카운터(7번, 호출부 라벨별·시간별 로컬 메모리 집계 + 정시 1줄 로그). 처리량 목표는 이 **계측된 클라이언트 요청 수**에 고정하며 `pg_stat_statements` 전역 수치로 대체하지 않는다(에이전트·대시보드 등 앱 밖 호출이 섞이기 때문).
**해석 규칙(사전 등록)**: ① 어떤 상관도 "원인 확정"이 아니다. 정지 중 델타가 정상 구간과 구조적으로 달라지는 항목(예: checkpointer sync_time, wal_bytes, 특정 relation의 reads)이 나오면 **후보 가설**로 올리고, 지원 답변·재현으로 확인한다. ② 앱 요청 수와 정지 시작의 선후·상관은 시각 정렬로만 주장한다. ③ \"호스트 I/O 정지\"는 상관 측정과 지원 확인 전까지 **가설**이라고 부른다. ④ 이 측정 어느 것도 변경을 일으키지 않는다(SELECT만, 통계 reset 금지).

## 5. 충돌 점검·병합 순서
- PR#75(#198)는 `bot_v5_legacy.py`의 `sb_get_all_strict`(키 일반화·headers 인자)·`sb_write_strict`·`run_geomnuri_patrol_once`를 바꾼다. 재시도·회로차단(R3)도 같은 `sb_*` 함수군을 건드리므로 **PR#75 병합 후 시작**하거나, R3를 신규 모듈(`sb_resilience.py`)로 만들어 `sb_h`·`sb_get_strict`·`sb_get_all_strict`·`sb_write_strict` 맨 앞에 호출 한 줄만 넣는 방식으로 충돌 면적을 줄인다.
- R2(순라 이벤트 읽기 병합)는 PR#75의 순라 코드 위에서만 가능 → PR#75 병합 후.
- R1(atlas 폴링)은 PR#75와 겹치지 않음(독립 PR 가능). PR#75의 쓰기 증가는 경보 발생 시에만(상태 전이 CAS 다단계): 정상 상태 추가 쓰기 0, 단 F1 정정으로 읽기가 회당 +1.
- **PR#75 충돌 현황(v1.1)**: PR#75 헤드가 23ec8aa로 바뀌었다(`ingestion` 점검이 `sb_get_all_strict` 2회 읽기 + 적체 요약, 프로브 도구 추가). R3·R2는 이 함수들을 건드리므로 PR#75 병합 전에는 시작하지 않는다. **Task#214의 R1~R4는 어느 것도 배포·병합하지 않는다(보류)**: 수정된 이 설계의 독립 검토와 대표 승인 이후에만 MAGI가 허가한다.
- 권장 순서: ① PR#75 검증·병합(마기 판정) ② **R0 계측 단독 PR(동작 변경 없음, 병합 후 최소 7일 기준선 수집)** ③ R1 단독 PR ④ R3(+R4) ⑤ R2. 각 단계 카산드라 HIGH 검증(감시 핵심 경로), 배포는 대표 승인·**업로드 없는 시간대**.
